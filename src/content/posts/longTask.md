# 如何处理长任务
一些小知识：浏览器给 setTimeout (0) 有最小 4ms 调度延迟，不是 0 毫秒，这是它天生缺陷。 
## 为什么需要拆分长任务
浏览器平均16.6ms渲染一帧，如果js线程一直停留在计算等庞大逻辑，占用线程时间成，有可能出现掉帧，页面卡顿
## 长任务定义
W3C 规范明确定义：主线程事件循环任务耗时 > 50ms，就判定为长任务。
## 如何处理
根据不同的情况去处理
类似于将这里：
// 一次性执行大循环，极易生成>50ms长任务，卡死主线程
```js
function heavyWork() {
  for(let i = 0; i < 10000; i++){
    // 很重的计算
    console.log(i)
  }
}
heavyWork()
```

改成这里
```js
let index = 0;
const TASK_BATCH_SIZE = 20; // 每一批处理20次，保证耗时 < 50ms
const TOTAL = 10000;

function processChunk(){
    // 处理一小批任务
    const end = index + TASK_BATCH_SIZE;
    for(; index < end && index < TOTAL; index++){
        // 繁重计算
        console.log(index)
    }

    // 如果还没做完，剩下的任务丢给下一轮宏任务
    if(index < TOTAL){
        setTimeout(processChunk, 0)
    }
}

processChunk()
```

但是有一定的局限性，这是将任务拆成一块一块，一个分片完成后让出线程，归还线程，如果分片设置不得当，也会出现掉帧，让出线程是在分片结束后而不是运行中
其次，分片只适用于可以被中途打断、允许穿插浏览器渲染、允许一点点延后完成的主线程繁重任务 
eg：
1. 大数据列表循环渲染（一次性渲染 10000 条 DOM 会卡，分批渲染）
2. 前端大数组遍历、数据预处理、数据转换
不适用于什么情况：
- 如果多段计算依赖同一个可变共享数据，两段之间不能留出窗口期让其他代码修改该数据，则不能使用 setTimeout 时间分片。
- 连续的一组 DOM 更新，如果不希望浏览器渲染出半成品中间状态，则不能拆分到多个 setTimeout 分片执行。
## 预处理 
### 预处理是什么
在真正需要使用结果之前，提前完成耗时计算、数据转换，把结果缓存起来。
### 什么时候用
接口请求数据拿到数据后，先渲染骨架屏、基础内容，这时可以后台慢慢预处理列表
甚至可以分片加预处理结合使用
- 预处理：目标 —— 提前把数据加工好，缓存结果，避免交互时现场计算卡顿
- 时间分片：目标 —— 把一段很重的同步任务切小块，分批跑，防止单次执行 > 50ms，产生长任务阻塞主线程
当然预处理加webworker也是可以的
### Webworker
Web Worker 允许 JS 创建一条独立于主线程的后台子线程。
主线程负责页面渲染、交互； Worker 线程专门跑 CPU 密集型、耗时很重的计算； 两条线程互不阻塞。

适用情况:CPU 密集型计算、耗时久、不需要操作 DOM、可以和 UI 并行执行
大文件加密哈希，文件清洗
